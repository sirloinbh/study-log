# #67 ID 검증 범위(15자리)와 응답 변환(::int) 불일치

- 이슈: [#67](https://github.com/sirloinbh/study-log/issues/67) (PR #66 리뷰에서 분리)
- 브랜치: `fix/67-bigint-ids`

## 문제

API의 경로·본문 ID 검증은 15자리 양의 정수(최대 999,999,999,999,999)까지 받는다. 하지만 조회 결과는 `id::int`로 변환했다. 그래서 행 ID가 2,147,483,647을 넘으면 "integer out of range"로 500이 났다. 테이블의 ID 열은 모두 `bigint`다.

## 결정

이슈가 제시한 두 방법 중 **응답을 bigint 범위에 맞추는 쪽**으로 통일했다.

- 검증 상한을 int 범위로 낮추면 bigint 열과 범위가 어긋난 채로 남는다. 또 여러 모듈의 검증을 고쳐야 한다.
- 15자리 이하 정수는 JS 숫자로 정확히 표현된다(2^53 미만). 그래서 응답을 숫자 그대로 유지해도 API 형식이 바뀌지 않는다.

## 변경

- `backend/src/app.ts`: pg의 `bigint`(int8, OID 20) 파서를 등록해 JS 숫자로 읽는다.
  - DATE 파서와 같은 방식이다.
  - 정확히 표현할 수 없는 값(2^53 이상)은 반올림하지 않고 오류로 거부한다. API로는 그런 ID를 만들 수 없다.
- `::int` 변환 10곳을 없앴다.
  - 대상 파일: `exercises.ts`, `keywords.ts`, `study-logs.ts`, `textbook-contents.ts`, `textbooks.ts`
  - 응답 필드 이름과 숫자 형식은 그대로다.
- 앱 코드에는 bigint를 돌려주는 집계(`count` 등)가 없다. 그래서 파서의 영향은 ID뿐이다. 테스트 코드의 `count(*)`는 모두 `::int`를 붙여 쓴다.

## 테스트

- `backend/test/bigint-ids.integration.test.ts`(실제 DB, 새 파일)
  - ID 3,000,000,000(int 범위 초과)과 999,999,999,999,999(15자리 최대)를 `OVERRIDING SYSTEM VALUE`로 직접 넣는다.
  - 응답의 ID가 정확한 숫자인지 확인한다.
    - 교재 조회, 목차 조회
    - 그 아래 절 추가(`parentId`)
    - 연습문제 조회, 정답 저장(`exerciseId`)
    - 학습 기록 추가(`textbookId`·`contentId`)
    - 키워드 조회
- 수정 전 코드에서 첫 확인(교재 3,000,000,000 조회)부터 실패하고, 수정 후 통과하는 것을 확인했다.

## 자동 코드 리뷰 1차

별도 읽기 전용 리뷰 에이전트가 검토했다. 지적이 없어 2차 리뷰는 하지 않는다. 분리할 이슈도 없다.

- 확인된 사항
  - ID 비교(목차 순서 변경의 `Set`, 트리 구성의 `Map`)는 모두 숫자 대 숫자 그대로다.
  - `::int AS id`를 없앤 뒤에도 조인 쿼리에 모호한 `id`가 없다.
  - 파서가 2^53 이상 값을 거부하면 pg가 쿼리를 실패로 돌려 일반 500이 된다. 프로세스는 멈추지 않는다.
  - 앱과 테스트에 다른 bigint 값(`count` 등)을 숫자로 잘못 읽는 곳이 없다.
- 참고(유지): 목차 순서 변경·목록 API는 큰 ID로 따로 테스트하지 않았다. 같은 코드 경로다.

## 한계·후속

- bigint 파서는 pg 모듈 전체에 적용된다. 나중에 bigint 집계(예: 큰 합계)를 추가하면 그 값도 숫자로 읽힌다. 2^53을 넘을 수 있는 값이면 별도로 다뤄야 한다.
